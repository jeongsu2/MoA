# Phase 0. 팀 시뮬레이션

> 작성: 2026-10-05 · 상태: **확정 (2026-10-05, 옵션 B 선택)** · 결정 기록: [ADR-001](decisions/ADR-001-team-composition.md) · 입력: [requirements.md](requirements.md)
> 서브에이전트 실제 정의 파일(`.claude/agents/*.md`)은 Phase 4(하네스 설계)에서 만든다. 여기서는 "누가, 무엇을, 언제" 하는지만 정한다.

## 1. 실제 회사라면 몇 명이 필요한가

MVP(회원, 글 작성, 댓글 선착순, 무통장 주문. 배송 조회는 D-02로 제외)를 약 3개월에 출시한다고 가정했다.

| 역할 | 인원 | 왜 필요한가 (이 서비스 기준) |
|---|---|---|
| PM / PO | 1 | 인플루언서 판매 흐름이 도메인 규칙 덩어리(3분 입금, 차순위 승계, 배송비). 규칙을 정하고 우선순위를 자르는 사람 |
| 백엔드 시니어 (테크 리드) | 1 | 선착순 동시성, 타이머 만료, 결제 상태 머신이 핵심 난제. 아키텍처와 ERD 책임 |
| 백엔드 개발자 | 1 | API, 인증, 주문·배송 구현 |
| 프론트엔드 개발자 | 1 | 모바일 웹, 블로그형 에디터 |
| 디자이너 | 1 | 네이버 블로그처럼 익숙한 UI, 모바일 댓글 UX |
| QA | 1 | 동시 댓글, 시간 초과, 권한(개인정보) 같은 경계 케이스 검증 |
| DevOps / SRE | 0.5 | 판매 오픈 순간 트래픽 버스트 대비, 배포·모니터링 (보통 겸직) |
| **합계** | **약 6.5명** | |

백엔드 지망이라는 목적상, 서브에이전트는 **백엔드 판단을 깊게 검증하는 역할**에 무게를 두고 프론트·디자인은 가볍게 둔다.

## 2. 서브에이전트 구성 옵션 (선택 필요)

| 옵션 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **A. 최소 (4개)** | pm, architect, backend-dev, reviewer | 관리 쉬움, 토큰 적음 | QA·면접 관점이 빠져 "왜"를 검증할 장치가 약함 |
| **B. 표준 (7개)** ⭐추천 | A + qa, frontend-dev, interviewer | 실제 팀 구조와 비슷하고, 면접관 에이전트가 학습 목적을 직접 겨냥 | 호출 규칙을 명확히 해야 함 |
| **C. 회사 완전 재현 (9개)** | B + designer, devops | 포트폴리오에서 팀 시뮬레이션을 가장 그럴듯하게 보여줌 | 개인 프로젝트에 과함. 디자인·인프라 에이전트는 호출 빈도가 낮음 |

**추천 이유(B):** 이 프로젝트의 목표는 기능이 아니라 면접 설명력이다. `interviewer`가 결정마다 압박 질문을 던지고, `qa`가 장애 시나리오를 만들면 ADR의 "버린 대안·장애 시나리오" 칸이 자연스럽게 채워진다. 디자인은 네이버 블로그 UI를 참고 기준으로 두면 별도 에이전트 없이 frontend-dev가 감당 가능하다.

## 3. 서브에이전트 정의 (옵션 C 기준 전체, B는 ⭐ 표시만 사용)

| 이름 | 책임 | 입력 | 출력 | 도구 | 호출 시점 |
|---|---|---|---|---|---|
| ⭐ `pm` | 요구사항·도메인 규칙 정리, 범위/비범위 결정 보조, 우선순위 | 사용자 요청, requirements.md | 유저 스토리, 수용 기준, 범위표 | Read, Write | Phase 1 시작, 기능 단위 계획 시 |
| ⭐ `architect` | 아키텍처·데이터 모델·기술 옵션 2~3개와 트레이드오프 제시 (결정은 사용자) | 요구사항, 리서치 노트 | ERD 초안, ADR 초안, 다이어그램 | Read, Write, WebSearch | Phase 1~2, 새 기술 결정 시 |
| ⭐ `backend-dev` | ERD·ADR대로 API·도메인 로직 구현, 테스트 작성 | 승인된 ERD, 기능 계획 | 코드, 테스트 | Read, Edit, Bash | Phase 5 구현 단계만 (ERD 승인 전 호출 금지) |
| ⭐ `frontend-dev` | 모바일 웹 화면, 블로그형 에디터, 댓글 UI | API 명세, 화면 요구 | 화면 코드 | Read, Edit, Bash | Phase 5, 백엔드 API 확정 후 |
| ⭐ `qa` | 경계·동시성·권한 테스트 시나리오, 장애 시나리오 도출 | ERD, 구현 코드 | 테스트 케이스, 부하 테스트 시나리오, 버그 리포트 | Read, Bash | ERD 리뷰 시, 각 기능 구현 후 |
| ⭐ `reviewer` | 코드 리뷰: ERD·ADR 위반, 보안, 성능 문제 지적 | diff, ERD, ADR | 리뷰 코멘트 | Read, Grep | 각 기능 구현 직후 |
| ⭐ `interviewer` | 결정·코드마다 면접 꼬리질문(설계 → 왜 → 트레이드오프 → 장애 가정 → CS 근거) | ADR, 코드, interview-questions.md | 질문 목록, 사용자 답변에 대한 피드백 | Read, WebSearch | ADR 작성 후, Phase 3, Phase 5 각 단계 끝 |
| `designer` | 화면 흐름, 와이어프레임 | 유저 스토리, 캡처 참고 | 화면 흐름도, 와이어프레임 | Read, Write | Phase 2 화면 정의 시 |
| `devops` | Docker, 배포, 모니터링, 부하 대비 | ERD 비기능 요구사항 | Dockerfile, compose, 배포 문서 | Read, Edit, Bash | Phase 5 인프라 단계 |

### 공통 규칙 (모든 에이전트)
- 결정을 대신하지 않는다. 옵션과 트레이드오프만 낸다.
- 산출물에 "왜, 버린 대안, 장애 시나리오"를 남긴다.
- 자기 Phase가 아니면 일하지 않는다 (예: ERD 승인 전 `backend-dev` 호출 금지).

## 4. 이 서비스에서 미리 보이는 핵심 면접 주제
- **선착순 동시성:** 같은 상품에 댓글 1,000개가 동시에 오면 누가 1등인가? (DB 락 vs Redis vs 큐)
  - 면접 질문 예시: "비관적 락과 낙관적 락 중 선착순 판정에 무엇을 쓰겠고, 그 이유는?"
- **시간 제한 예약:** 5분 미입금 자동 취소를 어떻게 구현하나? (스케줄러 폴링 vs Redis TTL/keyspace 이벤트 vs 지연 큐)
  - 면접 질문 예시: "서버가 재시작되면 진행 중이던 5분 타이머는 어떻게 되나요?"
