# Phase 1-3 보충. 실시간 반영 방식 자세히 비교

> 2026-10-12, 대상: MoA, 앞 문서: [03-auth-image-realtime.md](03-auth-image-realtime.md) 3장
> 인증은 세션(D-16)으로 정해졌다. 이 결정이 실시간 방식 선택에 영향을 준다(4장).
> 2026-10-12 결정(D-18): **짧은 폴링으로 시작**하고 부하 테스트로 측정한 뒤 SSE 전환 여부를 정한다.

## 0. MoA에서 실시간으로 보여줄 것
| 이벤트 | 누가 받나 | 늦으면 생기는 문제 |
|---|---|---|
| 새 댓글 | 글을 보는 모든 사람 | 내가 몇 번째인지 모름 (큰 문제는 아님) |
| ⭐ 당첨, 취소, 차순위 승계 | 글을 보는 모든 사람, 특히 당첨자 | **당첨자가 늦게 알면 5분을 날림** |
| 입금확인 완료 (자동 감사 댓글) | 당첨자 | 확인됐는지 몰라 불안 |
| 5분 남은 시간 | 당첨자 | 통신 불필요. 서버가 `deadline`만 주고 브라우저가 계산 |

모두 **서버 → 사용자** 방향이다. 사용자 → 서버(댓글 작성, 입금완료, 입금확인)는 일반 REST API로 충분하다.

## 1. 네 가지 방식이 동작하는 모양

```
짧은 폴링     브라우저 ──요청──▶ 서버   (2초마다 반복, 변화 없어도 응답)
             브라우저 ◀──응답── 서버

긴 폴링       브라우저 ──요청──▶ 서버   (변화가 생길 때까지 응답을 붙잡고 있음)
             브라우저 ◀──응답── 서버   (응답 받자마자 다시 요청)

SSE          브라우저 ──요청 1번──▶ 서버
             브라우저 ◀─이벤트─◀─이벤트─◀─이벤트── 서버  (연결 유지, 서버만 보냄)

WebSocket    브라우저 ──HTTP 업그레이드──▶ 서버 (101 Switching Protocols)
             브라우저 ◀═══양방향 메시지═══▶ 서버  (HTTP가 아닌 별도 프로토콜)
```

## 2. 항목별 비교

| 항목 | 짧은 폴링 | 긴 폴링 | SSE | WebSocket |
|---|---|---|---|---|
| 방향 | 사용자가 묻기만 함 | 사용자가 묻고 서버가 기다렸다 답 | 서버 → 사용자 | 양방향 |
| 프로토콜 | 일반 HTTP | 일반 HTTP | 일반 HTTP (`text/event-stream`) | `ws://`, `wss://` 별도 프로토콜 |
| 지연 | 폴링 간격만큼 (평균 간격의 절반) | 거의 즉시 | 거의 즉시 | 거의 즉시 |
| 서버가 붙잡는 것 | 없음 | 요청 하나씩 계속 | 연결 하나씩 계속 | 연결 하나씩 계속 |
| 끊겼을 때 | 다음 요청에서 자연 복구 | 다시 요청 | **브라우저가 자동 재연결**, `Last-Event-ID` 헤더로 마지막 이벤트 번호 전달 | 자동 재연결 없음, 직접 구현 |
| 데이터 형식 | 자유 (JSON) | 자유 | 텍스트만 (보통 JSON 문자열) | 텍스트, 바이너리 |
| 인증 (세션 쿠키) | 쿠키 자동 | 쿠키 자동 | 쿠키 자동. 단 `EventSource`는 **헤더를 직접 못 붙임** | 연결 시 쿠키 자동, 이후 메시지는 별도 |
| 프록시, 로드밸런서 | 문제없음 | 타임아웃 주의 | 버퍼링 끄기, 타임아웃 주의 | Upgrade 헤더 설정 필요, 타임아웃 주의 |
| 브라우저 연결 수 제한 | 없음 | HTTP/1.1이면 도메인당 6개 공유 | HTTP/1.1이면 도메인당 6개 (탭 여러 개면 부족), HTTP/2면 사실상 해결 | 별도 제한 (보통 넉넉함) |
| Spring 구현 | `@GetMapping` 그대로 | `DeferredResult` | `SseEmitter` (MVC) 또는 `Flux<ServerSentEvent>` (WebFlux) | `spring-websocket` + STOMP |
| 구현 난이도 | 가장 쉬움 | 중간 | 중간 | 가장 어려움 |

## 3. 판매 오픈 상황으로 계산해 보기
가정: 한 판매 글을 **500명**이 보고 있고, 오픈 후 1분 동안 댓글 300개, ⭐ 변화 20번.

| 방식 | 1분 동안 서버가 받는 요청 | 비고 |
|---|---|---|
| 짧은 폴링 (2초 간격) | 500명 x 30번 = **15,000번** | 대부분 "변화 없음" 응답. 간격을 늘리면 줄지만 ⭐가 늦게 보임 |
| 긴 폴링 | 이벤트 320번 x 500명 = 최대 **160,000번** 재요청 | 이벤트가 생길 때마다 500명이 **동시에 다시 요청**(몰림 현상). 이벤트가 잦은 MoA에는 오히려 불리 |
| SSE | 연결 500개 + 보내기 320번 x 500명 | 요청은 처음 500번뿐. 보내는 양은 같지만 HTTP 요청, 응답 헤더 비용이 없음 |
| WebSocket | SSE와 거의 같음 | 프레임 오버헤드가 더 작지만 MoA 규모에선 차이 미미 |

숫자는 가정이고, Phase 5에서 부하 테스트(k6, nGrinder)로 직접 재면 면접 소재가 된다.

## 4. MoA 결정(세션)과 엮이는 지점
- 브라우저 `EventSource`는 `Authorization` 헤더를 붙일 수 없다. **JWT였다면** 토큰을 URL 쿼리에 넣어야 해서 로그에 토큰이 남는 위험이 생긴다. **세션 쿠키(D-16)는 자동으로 같이 가서 이 문제가 없다.** SSE와 세션은 궁합이 좋다.
- WebSocket도 연결할 때 세션 쿠키를 쓸 수 있지만, 연결 후 세션이 만료돼도 연결이 살아 있는 문제를 따로 다뤄야 한다.

## 5. 각 방식을 고르면 챙겨야 할 것

### SSE
- **타임아웃:** `new SseEmitter()`를 그냥 쓰면 서버 기본 비동기 타임아웃(Tomcat 30초)으로 끊긴다. 시간을 직접 지정하고, 끊기면 브라우저가 재연결하게 둔다.
- **하트비트:** Nginx, AWS ALB 기본 유휴 타임아웃이 60초라 아무것도 안 보내면 끊긴다. 15~30초마다 빈 주석(`:`)을 보낸다.
- **버퍼링:** Nginx가 응답을 모았다 보내면 실시간이 아니게 된다. `X-Accel-Buffering: no` 헤더나 `proxy_buffering off`.
- **연결 관리:** 글 ID별로 `SseEmitter` 목록을 메모리(`ConcurrentHashMap`)에 들고, 완료, 타임아웃, 에러 때 반드시 지운다. 안 지우면 메모리 누수.
- **스레드:** Spring MVC의 `SseEmitter`는 서블릿 비동기라 연결을 유지하는 동안 **요청 스레드를 붙잡지 않는다**. 대신 연결 수(Tomcat 기본 `max-connections` 8192)가 한계가 된다.
- **놓친 이벤트:** 재연결 때 `Last-Event-ID`로 빠진 이벤트를 다시 보내거나, 더 단순하게 **재연결하면 댓글 목록 API를 한 번 다시 조회**한다. MoA는 후자로 충분하다.

### WebSocket
- 양방향이 필요해지면(예: 판매자와 구매자 1:1 채팅) 그때 의미가 커진다.
- 서버 여러 대면 STOMP 외부 브로커(RabbitMQ 등) 또는 Redis Pub/Sub가 필요.
- 재연결, 하트비트, 세션 만료 처리를 모두 직접 해야 한다.

### 짧은 폴링
- `If-None-Match`(ETag)나 "마지막 댓글 ID 이후만 달라"는 방식으로 응답을 작게 만들 수 있다.
- 사람이 적을 때는 가장 싸고 튼튼하다.

## 6. 서버가 여러 대가 되면
SSE, WebSocket 모두 "A 서버에 연결된 사용자에게 B 서버에서 생긴 ⭐를 보내야 하는" 문제가 생긴다.

| 방법 | 설명 | 트레이드오프 |
|---|---|---|
| Redis Pub/Sub | 이벤트를 Redis 채널에 발행, 모든 서버가 구독해서 자기 연결에 전달 | 단순하지만 **구독 중이 아닌 서버는 메시지를 못 받음**(fire and forget). MoA는 실시간을 보조 수단으로 두니(재연결 시 재조회) 허용 가능 |
| Redis Streams, Kafka | 이벤트를 로그로 저장, 서버가 이어서 읽음 | 유실 없음, 대신 복잡 |
| 스티키 세션 | 같은 글을 보는 사람을 같은 서버로 | 서버 하나에 몰리면 의미 없음 |

## 7. 모바일 환경 주의
- 인스타 인앱 브라우저(WebView)도 `EventSource`와 WebSocket을 대부분 지원하지만, 실제 기기에서 꼭 확인해야 한다.
- 모바일 브라우저는 화면을 끄거나 앱을 내리면 연결을 끊는다. 돌아왔을 때(`visibilitychange` 이벤트) **상태를 API로 다시 조회**해야 화면이 틀리지 않는다. 어떤 방식이든 필요하다.

## 8. 정리
| 방식 | MoA에 맞는 정도 | 한 줄 이유 |
|---|---|---|
| 짧은 폴링 | 시작점으로 좋음 | 가장 단순, 부하 측정의 비교 기준 |
| 긴 폴링 | 맞지 않음 | 이벤트가 잦아 재요청이 몰림 |
| SSE | **가장 잘 맞음** | 서버 → 사용자 방향만 필요, 세션 쿠키와 궁합, 자동 재연결 |
| WebSocket | 지금은 과함 | 양방향 기능(채팅)이 생기면 재검토 |

원칙: **실시간은 보조, 진짜 상태는 DB와 API.** 이벤트를 놓쳐도 재조회로 화면이 맞춰져야 한다.

- 면접 질문 예시: "SSE를 쓰면서 JWT 인증을 하려면 어떤 문제가 있나요?"
- 면접 질문 예시: "SSE 연결이 Nginx 뒤에서 60초마다 끊깁니다. 원인과 해결은?"
- 면접 질문 예시: "긴 폴링이 짧은 폴링보다 항상 좋은가요?"
