# Phase 1-3. 인증, 이미지 저장, 실시간 반영 리서치

> 2026-10-12, 대상: MoA, 백엔드: Java + Spring Boot (ADR-002)
> 관련 질문: R-10(인증), R-11(이미지), R-13(실시간).
> 2026-10-12 결정: 인증은 세션(D-16), 이미지는 로컬로 시작(D-17). 실시간은 폴링으로 시작해 측정(D-18). 이 문서는 옵션과 트레이드오프만 정리한다. 결정은 ERD 단계에서 정수님이 한다.

## 0. MoA에서 이 세 가지가 특별한 이유
- **유입 경로가 인스타 DM, 프로필 링크다.** 모바일 인앱 브라우저에서 바로 들어와 가입하고 댓글을 단다. 가입이 귀찮으면 첫 판매에서 이탈한다.
- **판매 오픈 순간에 트래픽이 몰린다.** 같은 글에 수백 명이 동시에 들어와 사진을 보고, 새로고침하며 ⭐를 기다린다.
- **"내가 당첨됐는지"와 "5분 남은 시간"을 바로 알아야 한다.** 늦게 알면 5분을 날린다.

## 1. 인증: 세션 vs JWT (R-10)

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 서버 세션 + 쿠키** | 로그인하면 서버가 세션을 만들고 `JSESSIONID` 쿠키로 식별. 서버가 여러 대면 Spring Session + Redis로 세션 공유 | Spring Security 기본 방식이라 자료가 많음. **강제 로그아웃, 정지가 즉시 됨**(세션 삭제). 토큰 탈취 대응이 쉬움 | 서버가 상태를 가짐. 다중 서버면 세션 저장소(Redis) 필요 |
| **B. JWT (Access + Refresh)** | 로그인하면 서명된 토큰 발급, 요청마다 헤더로 보냄. Access는 짧게, Refresh는 길게 | 서버가 상태를 안 가짐. 모바일 앱, 다른 서비스와 붙이기 쉬움 | **발급된 토큰은 만료 전까지 못 막음** → 막으려면 블랙리스트(결국 Redis). 저장 위치(localStorage면 XSS, 쿠키면 CSRF) 고민 필요. 구현할 게 많음 |
| **C. 소셜 로그인 (카카오, 네이버) + A 또는 B** | OAuth2로 로그인만 위임하고, 이후는 A나 B로 관리 | 인스타 유입 사용자의 **가입 장벽이 가장 낮음** | 실명, 전화번호를 카카오에서 받으려면 비즈 앱 전환과 검수가 필요. 결국 첫 로그인 후 "실명, 전화번호, 배송지" 추가 입력 화면이 따로 필요 |

**MoA 관점 메모**
- MoA는 웹앱 하나뿐이고 별도 모바일 앱이 없다. JWT의 가장 큰 장점(여러 클라이언트, 서비스 간 인증)이 아직 없다.
- 판매자가 악성 구매자를 막거나, 운영자가 계정을 정지하는 일이 생길 수 있다. 이건 세션이 훨씬 쉽다.
- 인플루언서(판매자)와 구매자 가입이 분리되어 있으니(F-01), 어느 방식이든 **역할(ROLE_SELLER, ROLE_BUYER)** 로 권한을 나눈다. [입금확인] 버튼(F-06b)은 "이 글의 판매자인가"까지 확인해야 한다(역할만으로는 부족).

- 면접 질문 예시: "세션 대신 JWT를 쓰면 로그아웃은 어떻게 구현하나요?"
- 면접 질문 예시: "판매자만 누를 수 있는 버튼을 프론트에서 숨기면 충분한가요?" (답의 방향: 아니다. 서버에서 글 작성자와 요청자를 비교해야 한다)

## 2. 이미지 저장 (R-11)

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 서버 로컬 디스크** | 업로드를 서버가 받아 디스크에 저장, 서버가 직접 서빙 | 가장 단순, 비용 없음 | 서버가 여러 대면 파일이 흩어짐. 서버 교체 시 유실. 판매 오픈 때 **이미지 요청이 API 서버 자원을 같이 먹음** |
| **B. S3 + 서버 경유 업로드** | 파일을 서버가 받아 S3에 올림 | 저장이 안전하고 서버를 늘려도 문제없음 | 큰 파일이 서버 메모리, 대역폭을 거쳐 감 |
| **C. S3 Presigned URL + CDN(CloudFront)** | 서버는 "올려도 되는 임시 URL"만 발급, 브라우저가 S3에 직접 업로드. 조회는 CDN | **API 서버가 파일을 아예 안 만짐.** 버스트 때 이미지가 CDN에서 나가 서버 부하가 거의 없음 | 업로드 완료 확인, 안 쓰인 파일 정리(고아 파일), URL 만료 시간 설계가 추가로 필요. AWS 비용 |

**MoA 관점 메모**
- 판매 글은 사진이 많고, 오픈 순간 수백 명이 같은 사진을 본다. 이미지가 가장 먼저 병목이 되기 쉬운 곳이다.
- DB에는 파일이 아니라 **이미지 키(경로)와 순서**만 저장한다. 그래서 ERD에 `post_image(post_id, image_key, sort_order)` 같은 테이블이 생길 가능성이 높다.
- 모바일에서 찍은 원본 사진은 크다. 리사이즈를 어디서 할지(브라우저에서 줄여서 올리기 vs 서버, Lambda에서 변환)도 정해야 한다.
- 학습 경로 제안: 로컬(A)로 기능을 먼저 만들고, 인터페이스(`ImageStorage`)로 감싸 두면 나중에 C로 바꿀 때 코드 수정이 작다.

- 면접 질문 예시: "이미지 업로드를 서버가 받지 않고 Presigned URL을 쓰는 이유는?"
- 면접 질문 예시: "업로드는 됐는데 글 저장이 실패하면 S3에 남은 파일은 어떻게 하나요?"

## 3. 실시간 반영: ⭐, 남은 시간, 새 댓글 (R-13)

> 자세한 비교: [03b-realtime-detail.md](03b-realtime-detail.md)

| 옵션 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 새로고침 / 짧은 폴링** | 몇 초마다 댓글 목록 API를 다시 호출 | 구현이 가장 쉽고 서버가 상태를 안 가짐 | 사람이 많으면 요청이 폭증(500명 x 2초마다 = 초당 250번). 변화가 없어도 계속 호출 |
| **B. SSE (Server-Sent Events)** | 브라우저가 연결 하나를 열어두고 **서버가 일방향으로** 이벤트를 밀어줌. Spring `SseEmitter` | HTTP 그대로라 단순, 끊기면 브라우저가 자동 재연결. MoA는 "서버 → 사용자" 알림이 대부분이라 잘 맞음 | 연결마다 서버 자원 사용. 서버가 여러 대면 이벤트를 모든 서버에 뿌릴 장치(Redis Pub/Sub 등) 필요. HTTP/1.1에서는 브라우저당 같은 도메인 연결 수 제한(6개) |
| **C. WebSocket (STOMP)** | 양방향 연결. Spring WebSocket + STOMP | 채팅처럼 양방향이 많을 때 강력 | MoA에 양방향이 필요한 곳이 거의 없음(댓글 작성은 일반 API로 충분). 프록시, 로드밸런서 설정, 다중 서버 브로커 등 복잡도가 가장 높음 |

**MoA 관점 메모**
- 실시간으로 알려야 할 것: (1) 새 댓글, (2) ⭐ 당첨과 취소, 차순위 승계, (3) 입금확인 완료. 모두 **서버 → 사용자** 방향이다.
- **5분 남은 시간은 실시간 통신이 필요 없다.** 서버가 `deadline`(마감 시각)만 내려주면 브라우저가 스스로 카운트다운한다. 단, 판정은 언제나 서버 시각 기준(1-2 문서의 조건부 UPDATE).
- 실시간 알림은 **놓쳐도 되는 보조 수단**으로 두고, 진짜 상태는 항상 API로 다시 조회할 수 있게 한다. 그래야 연결이 끊겨도 틀린 화면이 남지 않는다.
- 학습 경로 제안: 폴링(A)으로 시작해 부하 테스트로 요청 수를 재고, SSE(B)로 바꿔 줄어든 숫자를 비교하면 면접에서 말하기 좋다.

- 면접 질문 예시: "SSE와 WebSocket의 차이는 무엇이고, 이 서비스에서 무엇을 골랐나요?"
- 면접 질문 예시: "서버가 3대일 때 A 서버에 연결된 사용자에게 B 서버에서 생긴 당첨 이벤트를 어떻게 보내나요?"

## 4. 세 주제가 서로 엮이는 지점
- **Redis가 세 곳에서 등장한다:** 세션 저장(1-A 다중 서버), JWT 블랙리스트(1-B), SSE 다중 서버 이벤트 전달(3-B). 1-2의 당첨 판정까지 합치면 "Redis를 언제 넣을지"는 한 번에 정하는 게 낫다.
- **서버 한 대로 시작하면** 세션, 로컬 이미지, SSE 모두 Redis 없이 된다. 서버를 늘리는 순간 세 곳이 동시에 바뀐다. 이 순간을 "확장 단계"로 계획해 두면 좋다.
