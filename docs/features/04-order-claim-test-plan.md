## 0. 공통 규칙
- 종류: **단위** = 매칭 규칙 같은 순수 로직. **통합** = MockMvc + Testcontainers MySQL 8.4 (D-33). 행 락 동작 때문에 H2는 쓰지 않는다.
- 시각은 테스트용 `Clock` 빈을 주입해 고정한다. 클라이언트가 보낸 시각은 쓰지 않는다 (AC-10).
- 동시성 테스트는 `@Transactional` 롤백 없이, `CountDownLatch`로 동시 출발, **10번 반복**. 한 번이라도 깨지면 버그다. "가끔 실패"도 원인을 찾을 때까지 버그로 본다.
- 동시성 테스트 결과에 500이나 데드락 예외가 하나라도 있으면 실패다.
- 모든 통합 테스트 뒤에 **불변식 검사**를 SQL로 직접 한다.
  - I-1. 상품마다 진행 중 claim(WON, REPORTED)은 0개 또는 1개.
  - I-2. `product.current_claim_id`는 진행 중 claim의 id이고, 없으면 null. `status`는 진행 중이면 RESERVED, 없으면 ON_SALE.
  - I-3. `purchase_quota.active_count` = 그 글에서 그 사람의 WON, REPORTED, CONFIRMED claim 수, 그리고 5 이하.

## 5. 구현 전에 정할 것 (QA가 본 위험)
- Q-03: "quota 행이 없으면 먼저 만든다"를 조회 후 INSERT로 하면 동시 첫 댓글에서 중복 키 500이 난다. `INSERT ... ON DUPLICATE KEY UPDATE` 같은 방식을 backend가 정해야 한다.
- Q-02: quota UPDATE가 0행일 때 상품을 건드리기 전에 끝내야 한다. 상품을 먼저 RESERVED로 바꾸고 quota에서 실패하면 롤백 범위를 다시 봐야 한다.
- W-03 같은 100스레드 테스트는 커넥션 풀 크기(기본 10)보다 스레드가 많다. 대기 시간 초과로 실패하면 버그인지 설정인지 구분하도록 테스트 풀 크기와 락 대기 시간을 먼저 정한다.
