## 0. 공통 규칙
- 종류: **단위** = 산간 판별, 금액 계산. **통합** = MockMvc + Testcontainers MySQL 8.4 (D-33).
- 시각은 테스트용 `Clock` 빈으로 고정하고 테스트 안에서 옮긴다. 기준: 당첨 `won_at`=10:00:00, `deadline_at`=10:05:00.
- 만료 스케줄러는 테스트에서 자동 실행을 끈다. 만료가 필요하면 테스트가 직접 부른다 (06 계획과 같음).
- 동시성 테스트는 롤백 없이, `CountDownLatch`로 동시 출발, **10번 반복**. 500, 데드락 예외가 하나라도 있으면 실패.
- 모든 통합 테스트 뒤에 SQL로 **불변식 검사**:
  - I-1. claim 하나에 `orders`는 0개 또는 1개. REPORTED, CONFIRMED는 정확히 1개.
  - I-2. CONFIRMED claim 하나에 감사 SYSTEM 댓글은 정확히 1개, 그 외 상태는 0개.
  - I-3. claim 하나에 DEPOSIT_REPORT 댓글은 0개 또는 1개.
  - I-4. 04 계획의 I-1~I-3 (진행 중 claim 1개 이하, `current_claim_id`, quota 수).

## 4. 구현 전에 정할 것 (QA가 본 위험)
- R-03 멱등 응답: 진 요청은 claim 행 락을 기다린 뒤 UPDATE 0행을 받고 "현재 주문"을 다시 읽는다. 그 트랜잭션이 UPDATE 전에 일반 SELECT(예: 소유 확인용 `findById`)를 했다면 MySQL REPEATABLE READ 스냅샷이 그때 잡혀 **방금 커밋된 주문이 안 보인다.** 주문 없음, 404, 500 중 하나가 된다. 다시 읽는 방법(잠금 읽기 또는 새 트랜잭션)을 정해야 한다.
- 입금 안 됨(S-06)은 끝난 구매자 quota -1과 차순위 quota +1로 quota 행 두 개를 잡는다. 06 계획 S-06의 데드락 위험과 같다.
- S-04: 403과 404의 기준. 남의 claim 신고는 404(AC-7), 판매자 아닌 사람의 확인은 403(AC-16)으로 문서가 다르다. 둘 다 문서대로 검사한다.

## 5. 면접 질문 예시
"입금완료를 두 탭에서 동시에 눌렀을 때, 두 번째 요청도 200과 같은 주문을 돌려주려면 무엇을 조심해야 하나요?" (답의 방향: 조건부 UPDATE는 한쪽만 바꾼다. 진 쪽이 다시 읽을 때 트랜잭션 스냅샷이 이미 잡혀 있으면 새 주문이 안 보인다. 잠금 읽기로 최신 값을 읽는다)
