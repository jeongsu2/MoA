> 가정: 열린 질문은 모두 추천안으로 정해졌다고 본다 (Q-1 A 당첨된 적 없는 댓글 중 가장 작은 id, Q-2 A 예전에 써 둔 댓글도 후보, Q-3 A 스케줄러만 쓰기, 1초 간격).
> 2026-10-13, 작성: qa, 입력: [06-expiry.md](06-expiry.md), [requirements.md](../requirements.md) 8장, [erd-v2.md](../erd/erd-v2.md) 3장, 4장, [02 동시성](../research/02-concurrency-and-timer.md) 3장

## 0. 공통 규칙
- 종류: **단위** = 스케줄러 반복 로직. **통합** = Testcontainers MySQL 8.4 (D-33), 신고와 피드는 MockMvc.
- 시각은 테스트용 `Clock` 빈으로 고정하고 테스트 안에서 옮긴다. 기준: `won_at`=10:00:00, `deadline_at`=10:05:00.
- 테스트에서는 `@Scheduled` 자동 실행을 끄고, 만료 처리 메서드를 테스트가 직접 부른다. 자동 실행이 켜져 있으면 테스트끼리 결과가 섞여 "가끔 실패"가 생긴다.
- 동시성 테스트는 롤백 없이, `CountDownLatch`로 동시 출발, **10번 반복**. 500, 데드락 예외가 하나라도 있으면 실패.
- 모든 통합 테스트 뒤에 04 계획의 불변식 I-1~I-3 (상품마다 진행 중 claim 1개 이하, `current_claim_id`와 상태 일치, quota 수 일치)과 아래를 SQL로 검사한다.
  - I-4. 댓글 하나에 claim은 1개 이하 (`claim.comment_id` 유니크).

## 3. 구현 전에 정할 것 (QA가 본 위험)
- **시계 하나 (AC-8):** Clock 주입으로 테스트하려면 DB `NOW()`를 쓰면 안 된다. 앱 `Clock`에서 읽은 시각을 UPDATE 조건에 넘기는 방식으로 정해야 E-01, E-02, E-05를 쓸 수 있다.
- **경계 조건 글자 하나:** 신고는 `deadline_at > now`, 만료는 06 AC-2 `deadline_at <= now`인데 ERD 3장 예시는 `< NOW()`다. `<`로 구현하면 정확히 10:05:00에 둘 다 실패한다 (안전하지만 문서와 다름). 한쪽으로 맞춘다.
- **DATETIME 정밀도:** MySQL `DATETIME`(소수 초 없음)은 소수 초를 **버리지 않고 반올림**한다. 10:04:59.6이 10:05:00으로 저장되는 식이라 마감이 최대 0.5초 어긋난다. ddl-auto(D-36) 기본값은 보통 `datetime(6)`이지만 컬럼 정의를 직접 주면 바뀔 수 있다. `datetime(6)`으로 고정할지, 앱에서 초 단위로 자를지 정한다. E-05는 밀리초 차이를 쓰므로 정밀도가 정해져야 쓸 수 있다.
- **데드락 (S-06):** 만료와 입금 안 됨은 끝난 구매자 quota와 차순위 quota 두 행을 잡는다. 두 트랜잭션이 사람을 엇갈려 잡으면 데드락이다. ERD 4장 순서는 product와 quota 사이만 정했다. quota 두 행은 `user_id` 작은 순서로 잡거나, 데드락이 나면 만료는 다음 실행에서 재시도하고 입금 안 됨은 한 번 재시도하는 규칙이 필요하다.
- **스케줄러 자동 실행 끄기:** 테스트 프로필에서 끌 수 있는 설정이 있어야 한다. 테스트를 건너뛰는 것이 아니라 실행 시점을 테스트가 정하는 것이다.
