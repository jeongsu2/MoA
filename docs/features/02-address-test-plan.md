> 상태: **확정 (2026-10-13, 열린 질문 모두 추천안, D-34)**
> 2026-10-13, 작성: qa, 입력: [02-address.md](02-address.md), [requirements.md](../requirements.md) 8장, [erd-v2.md](../erd/erd-v2.md)

## 0. 공통 규칙
- 종류: **단위** = 서비스, 도메인 로직. **통합** = MockMvc + Testcontainers MySQL 8.4 (D-33). 행 락 동작 때문에 H2는 쓰지 않는다.
- 모든 테스트 뒤에 **불변식 검사**를 붙인다: 배송지가 1개 이상인 사용자는 `is_default=true`가 정확히 1개 (SQL로 직접 셈).
- 동시성 테스트는 `@Transactional` 롤백 없이, `CountDownLatch`로 동시 출발, **50번 반복**. 한 번이라도 깨지면 버그.
- 가입 때 만든 배송지 1개(기본)가 있는 상태에서 시작한다 (01 A-01).

## 3. 기본 변경
| ID | 시나리오 | 기대 결과 | 근거 | 종류 |
|---|---|---|---|---|
| S-01 | A(기본), B에서 B를 기본으로 | B만 true | AC-9 | 통합 |
| S-02 | 이미 기본인 A를 다시 기본으로, 같은 요청 3번 | 매번 200, 결과 같음 (멱등) | AC-9, 3장 PUT | 통합 |
| S-03 | **A, B, C에서 B 기본 요청과 C 기본 요청 동시** | 기본 정확히 1개, B 또는 C. 0개나 2개면 버그 | AC-10, Q-2 A | 통합, 동시성 |
| S-04 | **같은 B 기본 요청 연타 10건 동시** | 기본 1개 (B), 데드락이나 500 없음 | AC-10 | 통합, 동시성 |
| S-05 | **B 기본 요청과 "새 배송지 추가 setDefault=true" 동시** | 기본 1개 | AC-3, AC-10 | 통합, 동시성 |
| S-06 | **A(기본), B에서 "B 기본 요청"과 "B 삭제" 동시** | 기본 1개 (B 남고 기본이거나, B 지워지고 A가 기본). **기본 0개면 버그** | AC-8, AC-10 | 통합, 동시성 |
| S-07 | 없는 id를 기본으로 요청 | 404, **내 기존 기본 그대로** | Q-4 A | 통합 |
| S-08 | 사용자 2명이 각자 기본 변경 동시 | 서로 영향 없음, 둘 다 기본 1개씩 | AC-10 | 통합, 동시성 |

- S-06, S-07이 중요한 이유: Q-2 A의 `UPDATE address SET is_default = (id = ?) WHERE user_id = ?`는 대상 id가 내 배송지에 없으면 **내 배송지 전부를 false로 만든다.** 대상이 내 것인지 먼저 확인하거나(같은 트랜잭션에서 락), 바뀐 행 중 true가 1개인지 확인해야 한다. 삭제는 `is_default=false` 조건을 DELETE문에 넣어야 S-06에서 기본이 지워지지 않는다.

## 4. 권한 (IDOR)
사용자 X가 사용자 Y의 배송지 id로 요청한다. 모두 **404**(Q-4 A)이고, 응답 뒤 X와 Y의 배송지 행을 SQL로 비교해 하나도 안 바뀌었는지 본다.
| ID | 시나리오 | 기대 결과 | 근거 | 종류 |
|---|---|---|---|---|
| I-01 | Y의 id로 `PUT /api/me/addresses/{id}` | 404, Y 행 그대로 | AC-6 | 통합 |
| I-02 | Y의 id로 `DELETE` | 404, Y 행 남음 | AC-6 | 통합 |
| I-03 | **Y의 id로 `PUT .../{id}/default`** | 404, Y의 기본 그대로, **X의 기본도 그대로** (S-07과 같은 함정) | AC-6, Q-2 A | 통합 |
| I-04 | Y의 id와 없는 id의 응답 비교 | 상태 코드와 본문이 같음 (id가 있는지 드러나지 않음) | Q-4 A | 통합 |
| I-05 | X 목록, X의 `/api/me` 응답에 Y의 주소, 요청사항(공동현관 비밀번호) 없음 | 없음 | 5장 비기능 개인정보, D-14 | 통합 |
| I-06 | 판매자가 구매자 배송지 id로 요청 | 404 (판매자도 My 배송지 API로 남의 주소를 못 봄. 주소는 `orders`로만 공개) | ERD 5장 실명 노출 | 통합 |

## 6. 구현 전에 정할 것 (QA가 본 위험)
- C-06 개수 제한은 Q-2 A의 한 UPDATE문으로는 막히지 않는다. `users` 행을 `FOR UPDATE`로 잡을지, 11개를 드물게 허용할지 정해야 한다 (backend-dev가 옵션 제안, 정수 결정).
- AC-11(입금완료 순간의 기본 배송지가 주문에 들어감)과 "기본 변경과 입금완료 동시"는 입금완료 기능 테스트 계획에서 다룬다.
- 기능 문서에 목록의 기본 다음 정렬 순서가 없다. 테스트는 "기본이 맨 위"만 확인한다.

## 7. 면접 질문 예시
"`UPDATE ... SET is_default = (id = ?)` 한 줄로 기본 1개를 지킨다고 했는데, 남의 배송지 id를 넣으면 어떻게 되나요?" (답의 방향: WHERE에 해당 id가 없으니 내 배송지가 전부 false가 된다. 대상 소유를 먼저 확인하거나 결과 행을 검증해야 한다)
