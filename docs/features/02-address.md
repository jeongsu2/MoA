# 기능 02. My 배송지 관리

> 2026-10-13, 작성: pm, 상태: **확정 (2026-10-13, 열린 질문 모두 추천안, D-34)**
> 입력: [requirements.md](../requirements.md) F-01a, F-01b, D-10(D-24로 대체), D-24, D-25 / [erd-v2.md](../erd/erd-v2.md) `address`, `orders`

## 1. 유저 스토리
- US-1. 구매자로서, 우측 상단 My에서 내 배송지 목록과 기본 배송지를 한눈에 보고 싶다.
- US-2. 구매자로서, 선물이나 회사로 받으려고 배송지를 추가하고, 당첨 후 입금완료 전에 기본을 바꾸고 싶다 (D-24).
- US-3. 구매자로서, 이사하면 배송지를 고치거나 지우고 싶다. 이미 입금완료한 주문 주소는 그대로여야 한다.

## 2. 수용 기준 (Given / When / Then)

### 목록
- AC-1. Given 로그인 사용자, When 배송지 목록을 조회하면, Then 내 배송지만 오고 기본 배송지가 맨 위, `isDefault=true`는 정확히 1개다.

### 추가
- AC-2. Given 로그인 사용자, When 받는 사람, 전화번호, 우편번호, 주소1, 주소2, 배송 요청사항을 넣어 추가하면, Then 새 `address`가 생기고 기본은 바뀌지 않는다.
- AC-3. Given 추가 요청에 `setDefault=true`, When 저장하면, Then 새 배송지가 기본이 되고 기존 기본은 false가 된다 (한 트랜잭션).
- AC-4. Given 필수값 누락이나 형식 오류, When 추가하면, Then 400과 틀린 필드 안내.

### 수정
- AC-5. Given 내 배송지, When 수정하면, Then 그 행이 바뀐다. Given 이미 입금완료(`orders` 생성)된 주문, Then 주문의 주소 스냅샷은 바뀌지 않는다 (ERD v2 `orders`).
- AC-6. Given 다른 사람의 배송지 id, When 조회, 수정, 삭제, 기본 변경을 하면, Then 거부되고 아무것도 안 바뀐다. (403 vs 404는 Q-4)

### 삭제
- AC-7. Given 기본이 아닌 내 배송지, When 삭제하면, Then 목록에서 사라진다. 이미 생긴 주문에는 영향이 없다 (스냅샷).
- AC-8. Given 기본 배송지 또는 마지막 1개, When 삭제하면, Then 규칙은 Q-1에 따름. 어떤 경우든 삭제 후 배송지가 있으면 기본은 정확히 1개다.

### 기본 변경
- AC-9. Given 배송지 2개 이상, When 다른 배송지를 기본으로 바꾸면, Then 그것만 `is_default=true`, 나머지는 false.
- AC-10. Given 같은 사용자가 기본 변경을 두 번 동시에 보냄 (두 탭, 연타), When 둘 다 처리되면, Then 기본은 정확히 1개다 (방법은 Q-2).
- AC-11. Given 당첨(WON) 상태, When 입금완료 전에 기본을 바꾸고 입금완료를 누르면, Then 주문에는 바꾼 기본 배송지가 들어간다 (D-24). 이 연결은 입금완료 기능 문서에서 검증.

### 화면 안내
- AC-12. Given My 배송지 화면, Then "주문에는 입금완료를 누를 때의 기본 배송지가 들어갑니다" 안내가 보인다 (D-24 문구와 맞춤).

## 3. 제안 API
| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| GET | `/api/me/addresses` | 없음 | 200, [id, recipientName, recipientPhone, zipCode, address1, address2, deliveryNote, isDefault] |
| POST | `/api/me/addresses` | recipientName, recipientPhone, zipCode, address1, address2, deliveryNote, setDefault | 201, 배송지 1개 |
| PUT | `/api/me/addresses/{id}` | recipientName, recipientPhone, zipCode, address1, address2, deliveryNote | 200, 배송지 1개 |
| DELETE | `/api/me/addresses/{id}` | 없음 | 204 |
| PUT | `/api/me/addresses/{id}/default` | 없음 | 200, 바뀐 목록 (같은 요청을 여러 번 보내도 결과 같음) |

- 경로에 userId를 넣지 않는다. 사용자는 세션에서 꺼낸다 (남의 id를 넣는 요청 자체가 불가능).
- 기본 변경을 PUT으로 둔 이유: 몇 번 보내도 결과가 같은(멱등) 동작이라서.

## 4. 범위 밖
- 주소 검색 API 연동 방식 (프론트 결정, Q-3)
- 제주 산간 판별 (R-12, 입금완료와 배송비 기능에서)
- 입금완료 때 `orders` 스냅샷 생성 (입금완료 기능 문서에서)
- 배송지 별칭 ("집", "회사"): ERD v2에 컬럼 없음, 원하면 v3
- 배송지 정렬 순서 바꾸기

## 5. 열린 질문 (정수 결정 필요)
| ID | 질문 | 옵션 (트레이드오프) | 추천 |
|---|---|---|---|
| Q-1 | 기본 배송지와 마지막 1개 삭제 | A. 기본은 삭제 불가, 다른 걸 기본으로 바꾼 뒤 삭제 (규칙 단순, 한 번 더 눌러야 함) / B. 기본 삭제 시 가장 최근 배송지가 자동 기본 (편하지만 원치 않는 주소가 기본이 될 수 있음, 5분 안 입금 중이면 위험) / 공통: 마지막 1개는 삭제 불가 (D-24 기본 배송지 필수) | A |
| Q-2 | 기본 1개 보장 방법 (MySQL은 부분 유니크 인덱스가 없음) | A. 한 UPDATE문으로 처리: `UPDATE address SET is_default = (id = ?) WHERE user_id = ?` (ERD 그대로, InnoDB 행 락이 동시 요청을 줄 세움) / B. `users` 행을 `SELECT ... FOR UPDATE`로 잡고 두 단계 UPDATE (흐름이 눈에 잘 보이지만 락 범위가 넓음) / C. `default_user_id` 같은 생성 컬럼에 유니크 (DB가 강제하지만 ERD v3 필요) | A |
| Q-3 | 주소 입력 방식 | A. 우편번호 검색(카카오 우편번호 서비스) 결과만 입력, 상세주소만 타이핑 (우편번호 정확, 산간 판별 R-12에 유리) / B. 전부 직접 타이핑 (외부 의존 없음, 우편번호 오타 위험) | A |
| Q-4 | 남의 배송지 id 요청 시 응답 | A. 404 (있는지조차 숨김) / B. 403 (의미가 정확하지만 id 존재가 드러남) | A |
| Q-5 | 배송지 최대 개수 | A. 제한 없음 (단순) / B. 10개 (악용과 화면 길이 제한, 검사 하나 추가) | B |
| Q-6 | 진행 중 당첨(WON)이 있을 때 기본 배송지 삭제, 수정을 막나? | A. 막지 않음 (D-24대로 입금완료 순간의 기본을 쓰면 됨, 단순) / B. 막음 (실수 방지, D-24 "입금완료 전에 수정" 안내와 충돌) | A |

## 6. 관련 결정
F-01a, F-01b, D-01, D-10(대체됨), D-24, D-25, D-27(ERD v2)

## 7. 면접 질문 예시
