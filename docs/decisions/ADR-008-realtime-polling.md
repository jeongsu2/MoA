# ADR-008. 실시간 반영: 짧은 폴링으로 시작, 측정 후 SSE 전환 판단

- 결정: 2026-10-12 (D-18), 결정자: 정수, 상태: 확정
- 정리: 2026-11-15 (결정 뒤에 정리함)
- 관련: [03 리서치 3장](../research/03-auth-image-realtime.md), [03b 리서치](../research/03b-realtime-detail.md), 구현 #29 (피드 `afterId` API)

## 결정
- 새 댓글, ⭐ 당첨과 승계, 입금확인은 화면이 몇 초마다 피드 API를 다시 부르는 **짧은 폴링**으로 보여 준다. "마지막 댓글 id 이후만" 받아서 응답을 작게 한다.
- 5분 남은 시간은 서버가 `deadline_at`만 주고 브라우저가 스스로 센다. 판정은 항상 서버가 한다.
- 부하 테스트로 요청 수를 잰 뒤 SSE로 바꿀지 정한다.

## 이유
- 가장 단순하고 서버가 연결 상태를 들고 있지 않는다. 서버를 늘려도 바뀔 게 없다.
- 실시간은 보조 수단이고 진짜 상태는 DB와 API다. 어떤 방식이든 재조회는 필요하니 폴링이 기본이 된다.
- 폴링 숫자를 기준선으로 남겨야, SSE로 바꿀 때 "얼마나 줄었는지"를 숫자로 말할 수 있다.

## 버린 대안
- **처음부터 SSE:** MoA에 가장 잘 맞지만(서버 → 사용자 방향만 필요, 세션 쿠키와 궁합), 연결 관리, 타임아웃, 하트비트, 다중 서버 이벤트 전달을 먼저 만들어야 한다.
- **긴 폴링:** 이벤트가 잦은 판매 오픈 때 이벤트마다 모두가 동시에 다시 요청해서 오히려 불리하다.
- **WebSocket:** 양방향이 필요한 곳이 없다. 설정과 운영이 가장 복잡하다.

## 장애 시나리오 / 리스크
- 판매 오픈 때 요청이 몰린다 (가정: 500명이 2초 간격이면 1분에 15,000번).
- ⭐가 폴링 간격만큼 늦게 보인다.
- `afterId` 방식은 작은 id 댓글이 늦게 커밋되면 영원히 놓칠 수 있다 → 최근 몇 초 댓글을 겹쳐 받는 조건으로 막음 (#29 리뷰에서 잡음).

## 다시 볼 조건
- 부하 테스트에서 폴링 요청이 서버 한계에 닿거나, ⭐ 지연이 문제가 될 때 (SSE 전환).

## 면접 질문 예시
"긴 폴링이 짧은 폴링보다 항상 좋은가요? 이 서비스에서 SSE로 바꾼다면 무엇을 측정해서 결정하나요?"
