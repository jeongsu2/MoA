# ADR-007. 5분 만료와 승계: DB 폴링 스케줄러 (`@Scheduled`)

- 결정: 2026-10-12 (ERD v2 승인 D-27, 5분 규칙 D-04, D-07), 결정자: 정수, 상태: 확정
- "Redis 없이 DB 스케줄러"는 따로 정한 D-xx가 없고, ERD v2 4장의 추천 기본값을 승인하면서 정해짐.
- 세부(1초 간격, 한 번에 100개, claim마다 트랜잭션, 앱 `Clock`, `<=` 경계, 조회 때 지연 평가 안 함): 2026-10-13, 06 기능 문서 추천안과 구현 기준의 Claude 기본값, **정수 확인 전**
- 정리: 2026-11-15 (결정 뒤에 정리함)
- 관련: [02 리서치 3장](../research/02-concurrency-and-timer.md), [06-expiry.md](../features/06-expiry.md), [ADR-006](ADR-006-claim-lock.md), 구현 #31

## 결정
- 당첨 때 `claim.deadline_at`을 DB에 저장한다.
- `@Scheduled(fixedDelay = 1000)` 스케줄러가 앞 실행이 끝나고 1초 뒤에 다시 돌면서 `deadline_at <= now`인 WON claim을 100개까지 읽고, claim마다 따로 트랜잭션을 열어 만료와 차순위 승계를 한다.
- 만료와 승계는 스케줄러만 한다. 피드 조회는 쓰기를 하지 않는다.
- 시각은 앱 `Clock` 하나에서 읽는다 (DB `NOW()` 안 씀).

## 이유
- 마감 시각이 DB에 있어서 서버가 재시작돼도 타이머가 사라지지 않는다. 다시 뜨면 밀린 만료부터 처리한다.
- 상태 변경은 [ADR-006](ADR-006-claim-lock.md)의 product 락 + 조건부 UPDATE를 그대로 쓴다. 스케줄러가 겹쳐 돌아도, 4분 59초 입금완료와 만료가 동시에 와도 한쪽만 성공한다 (정확히 한 번).
- claim마다 트랜잭션을 나눠서 하나가 실패해도(데드락, 락 대기 초과) 나머지는 처리된다. 실패한 claim은 WON 그대로라 다음 실행에서 다시 한다.
- 새 인프라 없이 Spring 기본 기능만 쓴다.
- `Clock`을 쓰면 테스트에서 시각을 고정할 수 있고, 5분 경계(정확히 5분 0초는 만료)를 한 기준으로 맞춘다.

## 버린 대안
- **Redis TTL + 만료 알림:** 알림이 "fire and forget"이라 서버가 끊겨 있으면 이벤트가 사라지고, 실제 삭제 시점에 나와 늦을 수 있다.
- **지연 큐(Redis Sorted Set, RDelayedQueue, RabbitMQ):** 정시에 가깝지만 큐 인프라가 늘고, 큐와 DB가 어긋날 때 복구 설계가 필요하다.
- **조회 때 지연 평가 같이 쓰기:** ERD에는 있었지만, 조회 API가 쓰기를 하게 되어 락과 트랜잭션이 복잡해진다. 1초 간격이면 화면 차이가 작아서 뺐다 (06 Q-3, 정수 확인 전).

## 장애 시나리오 / 리스크
- 최대 약 1초(와 처리 시간)만큼 늦게 만료된다. 구매자 화면 카운트다운은 `deadline_at`으로 따로 돈다.
- 서버를 2대로 늘리면 스케줄러가 양쪽에서 돈다. 조건부 UPDATE로 결과는 맞지만 일이 겹친다 → ShedLock이나 `FOR UPDATE SKIP LOCKED`.
- 한 번에 100개만 읽어서, 100개 넘게 계속 실패하면 뒤 claim 만료가 밀린다 (지금 규모에선 그대로).

## 다시 볼 조건
- 서버를 늘릴 때, 만료 지연이 사용자 불만으로 이어질 때.

## 면접 질문 예시
"5분 타이머가 도는 중에 서버가 재시작되면 어떻게 되나요? Redis 만료 이벤트만 쓰면 왜 위험한가요?"
