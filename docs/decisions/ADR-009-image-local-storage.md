# ADR-009. 이미지 저장: 서버 로컬 디스크 + `ImageStorage` 인터페이스

- 결정: 2026-10-12 (D-17), 결정자: 정수, 상태: 확정
- 정리: 2026-11-15 (결정 뒤에 정리함)
- 관련: [03 리서치 2장](../research/03-auth-image-realtime.md), [03-post.md](../features/03-post.md), 구현 #28 (`ImageStorage`, `LocalImageStorage`)

## 결정
- 판매 글 이미지는 서버가 받아서 로컬 디스크에 저장하고 직접 내려준다.
- 저장은 `ImageStorage` 인터페이스로 감싸고, 지금 구현은 `LocalImageStorage` 하나다.
- DB에는 파일이 아니라 이미지 키와 순서(`post_image`)만 저장한다.

## 이유
- 지금은 서버 1대, 로컬 개발뿐이다. 클라우드 계정과 비용 없이 기능을 먼저 끝낼 수 있다.
- 인터페이스로 감싸 두면 S3로 바꿀 때 구현 클래스 하나만 추가하면 된다. 글 저장 로직은 안 바뀐다.
- DB에 키만 두면 저장소를 바꿔도 테이블은 그대로다.

## 버린 대안
- **처음부터 S3 (서버 경유 업로드):** 저장은 안전하지만 지금 단계에서 계정, 권한, 비용 설정이 먼저 필요하다.
- **S3 Presigned URL + CDN:** 판매 오픈 때 서버 부하가 가장 적지만, 업로드 완료 확인, 고아 파일 정리, URL 만료 설계가 추가로 필요하다.

## 장애 시나리오 / 리스크
- 판매 오픈 때 수백 명이 같은 사진을 받으면 이미지 요청이 API 서버 자원을 같이 쓴다.
- 서버를 바꾸거나 디스크가 날아가면 파일이 사라진다.
- 서버를 2대로 늘리면 파일이 서버마다 흩어진다.

## 다시 볼 조건
- 운영 배포 전 (S3 전환), 부하 테스트에서 이미지 요청이 병목일 때 (CDN).

## 면접 질문 예시
"이미지 업로드를 서버가 받지 않고 Presigned URL로 바꾸면 무엇이 좋아지고, 무엇을 새로 챙겨야 하나요?"
