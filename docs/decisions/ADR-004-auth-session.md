# ADR-004. 인증: 서버 세션 + 쿠키 (Spring Security 기본)

- 결정: 2026-10-12 (D-16), 세부 2026-10-13 (D-34), 결정자: 정수, 상태: 확정
- 정리: 2026-11-15 (결정 뒤에 결정 로그와 리서치로 정리함)
- 관련: [03 리서치 1장](../research/03-auth-image-realtime.md), [01-auth.md](../features/01-auth.md), 구현 #26

## 결정
로그인은 Spring Security 기본 방식인 서버 세션과 `JSESSIONID` 쿠키로 한다. 세션은 7일, 쓰기 요청은 CSRF 토큰으로 막는다. 소셜 로그인은 나중에 한다.

## 이유
- MoA는 웹앱 하나뿐이다. JWT의 큰 장점(여러 클라이언트, 서비스 사이 인증)이 아직 없다.
- 판매자가 악성 구매자를 막거나 운영자가 계정을 정지할 때, 세션은 지우면 바로 끝난다. JWT는 만료 전까지 못 막아서 결국 블랙리스트 저장소가 필요하다.
- 나중에 SSE로 바꿀 때 궁합이 좋다. 브라우저 `EventSource`는 `Authorization` 헤더를 못 붙이지만 쿠키는 자동으로 간다 ([03b 리서치 4장](../research/03b-realtime-detail.md)).
- Spring Security 기본값이라 직접 짤 코드가 적고 자료가 많다.

## 버린 대안
- **JWT (Access + Refresh):** 서버가 상태를 안 가지지만, 로그아웃과 정지를 즉시 못 하고 토큰 저장 위치(XSS, CSRF)와 재발급을 직접 설계해야 한다.
- **처음부터 소셜 로그인:** 가입 장벽은 가장 낮지만, 실명과 전화번호를 받으려면 비즈 앱 검수가 필요하고 추가 입력 화면이 따로 생긴다.

## 장애 시나리오 / 리스크
- 서버를 2대 이상으로 늘리면 세션이 서버마다 따로 있어 로그인이 풀린다 → Spring Session + Redis로 세션을 공유한다.
- 세션 7일은 쿠키를 도둑맞으면 위험 기간이 길다 (D-34에서 받아들임).
- 쿠키 인증이라 CSRF 공격 대상이 된다 → CSRF 토큰, 로그인 때 토큰 교체.

## 다시 볼 조건
- 서버를 늘릴 때 (세션 저장소), 모바일 앱이나 외부 서비스가 붙을 때 (JWT 재검토).
