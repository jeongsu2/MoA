# ADR-006. 선착순 당첨: product 행 비관적 락 + 조건부 UPDATE (Redis 없이 DB만)

- 결정: 2026-10-12 (ERD v2 승인 D-27, D-20, D-22), 결정자: 정수, 상태: 확정
  - "Redis 없이 DB만"은 따로 정한 D-xx가 없고, ERD v2 4장의 추천 기본값을 승인하면서 정해짐.
- 세부 기준(결정 1의 "모든 상태 전이가 product 먼저", 락 순서, READ COMMITTED): 2026-10-13, Claude 기본값, **정수 확인 전**
- 정리: 2026-11-15 (결정 뒤에 정리함)
- 관련: [02 리서치 1, 2장](../research/02-concurrency-and-timer.md), [erd-v2.md](../erd/erd-v2.md), [claim-implementation-notes.md](../features/claim-implementation-notes.md), 구현 #29, #30

## 결정
1. claim 상태를 바꾸는 모든 트랜잭션(당첨, 입금완료, 입금확인, 입금 안 됨, 만료)은 먼저 `product` 행을 `SELECT ... FOR UPDATE`로 잠근다. 같은 상품의 요청은 한 줄로 선다.
2. 그다음 claim을 **조건부 UPDATE**(상태 조건 포함)로 바꾸고, 바뀐 행 수로 성공을 판단한다. 상품당 진행 중 당첨은 `product.current_claim_id`로 하나만 둔다.
3. "먼저"의 기준은 **product 락을 잡은 순서**. 차순위는 댓글 id 순서 (D-22).
4. 1인 5개 제한은 `purchase_quota`의 조건부 UPDATE(`active_count < 5`)로 센다. 첫 행은 `INSERT ... ON DUPLICATE KEY UPDATE`로 만들고 잠근다. 락 순서는 product가 항상 먼저이고, 그 뒤에 purchase_quota(두 행이면 `user_id` 작은 순서)나 users를 잡는다. users를 product보다 먼저 잡지 않는다.
5. 락보다 먼저 claim을 읽는 상태 전이 트랜잭션은 `READ COMMITTED`로 연다.

## 이유
- 당첨은 틀리면 안 되는 **정합성** 문제다. 마지막 방어선은 어차피 DB 조건이어야 한다 (Kleppmann의 효율용 락과 정합성용 락 구분). DB 하나로 끝내면 저장소 사이 불일치가 아예 없다.
- 락 잡은 순서 = 당첨 순서라 "먼저"를 한 문장으로 정의할 수 있다.
- 조건부 UPDATE를 같이 쓰면 스케줄러가 두 번 돌거나, 입금완료와 만료가 동시에 와도 한쪽만 성공한다.
- 락 순서를 고정하면 두 락(product, quota)을 잡아도 데드락 사이클이 생기지 않는다.
- MySQL 기본인 REPEATABLE READ는 첫 읽기에서 스냅샷이 잡힌다. 락 전에 claim을 읽으면 락 뒤의 일반 SELECT가 앞 요청의 커밋을 못 본다. 그래서 RC로 연다 (일부러 RR로 돌려 테스트가 실패하는 것을 확인함).
- 학습 순서: DB 락으로 먼저 만들고, 부하 테스트로 한계를 잰 다음, 필요하면 Redis나 큐로 바꾼다. 바꿀 때 숫자로 이유를 말할 수 있다.

## 버린 대안
- **낙관적 락(`@Version`):** 선착순처럼 충돌이 몰리는 곳에서는 재시도가 폭증한다.
- **조건부 UPDATE만:** 락이 짧아 빠르지만, 당첨 순서가 커밋 순서라 댓글 id 순서와 어긋날 수 있고, 진 요청을 차순위로 두는 설계가 따로 필요하다.
- **Redis 원자 연산, Redisson 분산 락:** 빠르지만 Redis와 DB가 어긋날 수 있고, Redis 장애 때 판정을 못 한다. 서버 1대에서는 얻는 게 적다.
- **큐로 줄 세우기(Kafka, Redis Stream):** 순서는 완벽하지만 ⭐가 늦게 붙고 인프라가 가장 복잡하다.
- **락 뒤 읽기를 모두 `FOR SHARE`로:** 하나라도 빠뜨리면 깨진다. **claim을 먼저 잠그기:** product → claim 순서와 반대라 데드락.

## 장애 시나리오 / 리스크
- 인기 상품 한 행에 요청이 몰리면 락 대기열이 생기고 커넥션 풀이 마를 수 있다 → 부하 테스트(k6)로 측정할 것.
- 거의 동시에 온 댓글에서 화면상 뒤 댓글이 당첨될 수 있다 (D-22, 드묾).
- 승계 때 quota를 순서 밖에서 잡는 예외가 있어 드물게 데드락 → 만료는 다음 실행에서 재시도, [입금 안 됨]은 409 (받아들인 위험).
- `isolation`은 새 트랜잭션에만 걸린다. 바깥 트랜잭션 안에서 부르면 조용히 RR로 돈다 → 이런 메서드는 트랜잭션 없이 부른다.

## 다시 볼 조건
- 부하 테스트에서 락 대기로 응답 시간이나 커넥션 풀이 한계에 닿을 때 (Redis 판정이나 큐 검토).
