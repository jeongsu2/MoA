# 학습 포인트 05. 입금완료 신고와 판매자 입금확인 (#30)

## 핵심 개념
- **스냅샷 저장 (D-24):** 주문에 주소를 참조하지 않고 복사함. 나중에 기본 배송지를 바꿔도 끝난 주문 주소는 그대로. 정규화보다 "그 시점의 사실"이 중요한 데이터
- **멱등성과 유니크:** 입금확인을 두 번 눌러도 조건부 UPDATE가 1행일 때만 감사 댓글을 씀. `orders.claim_id` 유니크가 마지막 방어선
- **REPEATABLE READ 스냅샷 함정:** MySQL 기본 격리 수준에선 트랜잭션의 첫 일반 SELECT 때 스냅샷이 고정됨. 락을 기다린 뒤 읽어도 앞 요청이 커밋한 결과가 안 보임. 그래서 입금 동작은 READ COMMITTED로 엶 (일부러 되돌려 보니 테스트 3개 실패)
- **인가는 서버에서:** [입금확인] 버튼을 화면에서 숨기는 것만으론 부족. 서버가 글 작성자와 요청자를 비교해 403

## 면접 질문 3개
1. 주문에 배송지를 복사해 저장한 이유는? 정규화 위반 아닌가요? (그 시점의 사실을 남김)
2. MySQL 기본 격리 수준에서 락을 잡은 뒤에도 옛날 데이터가 보인 이유와 해결법은? (첫 읽기 스냅샷, READ COMMITTED 또는 잠금 읽기)
3. 판매자가 입금확인을 빠르게 두 번 누르면 감사 댓글이 두 번 달리지 않게 어떻게 막았나요? (조건부 UPDATE 바뀐 행 수)
